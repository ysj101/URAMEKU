# ウラメク V2 — 事件制作ガイド

JSON (`data/cases/*.json`) を唯一の正本とする。旧形式の詳細は `archive/game-v1/CASE_AUTHORING.md`。V2では `schemaVersion: 2` と `v2` を指定する。旧フィールドは移行互換用に残せるが、V2の評価とUIで計算・3断片・単一照合を要求しない。

## 制作手順

1. 架空の事件で検証できる事実、出典、期間・対象、未確認事項を定義する。旧事件の数値・分母を都合で変えない。
2. `v2.modes` に decoding / experiment / decision を列挙し必要な操作を設計する。
3. 解読の問い・選択肢・根拠を定義する。複数の妥当な解釈には複数のaccepted選択肢を設ける。acceptedは事実と根拠の整合に対する検証で、人格や価値判断の正解ではない。
4. `v2.graph.paths` に必要な根拠リンク集合を複数経路で定義する。リンクは異なる資料を from / to とし、supports / contradicts / qualifies / sequence の関係を持つ。問いは比較する役割を伝え、資料名で答えを漏らさない。
5. 心理実験は条件・共通選択肢・開示資料・比較の問い・限界を定義する。初回の選択を保存してから対照を示す。両反応・不変でも完了できる。
6. 意思決定は目的・資源・複数選択肢・費用・結果・トレードオフ・追加情報を定義する。保留を設け、少なくとも2つの実行可能な方針を用意する。結果を方針の正誤にしない。
7. 報告の問い・種明かし・留保・再挑戦を用意し、主経路と別経路を予算内で検証する。
8. プレイヤーに見える文章を「文章の書き方」の手順で整え、`npm run lint:wording` を通す。
9. 「ケース一覧の画像」の手順で、その事件専用の画像を作成し、一覧での表示を確認する。

## ケース一覧の画像

ケースを追加するときは、内容に合う画像も1枚作る。共通の書類に事件名を入れるだけにせず、その事件を表す場面や小物を主役にする。既存のケースと並べたときに見分けられる構図にする。

### 作成方針

- 世界観は [ART_BIBLE.md](ART_BIBLE.md) と `design/reference/c2-canonical-board.png` に合わせる。紙の切り絵、黒い印刷、擦れた紙の質感を使い、赤と青を差し色にする。
- 主役は1つ、主な要素は3つ以内を目安にする。余白を取り、細かな飾りや過剰な陰影を避ける。立体的な3D表現や写真調にしない。
- 画像内にはケース番号、タイトル、文章、数値、ロゴを入れない。意味のない文字らしき模様も入れない。必要な情報はHTMLで表示する。
- キャラクターの顔やシルエットを新しく生成しない。登場させる場合は既存の正本素材を使う。
- 画像は事件の入り口として使う。答えを明かしたり、資料にない事実や数値を足したりしない。
- AIで作成する場合は imagegen スキルを使い、ケースごとに生成する。使用したツール、最終プロンプト、保存先を `docs/reviews/` に記録する。[今回のプロンプト例](reviews/case-cover-prompts-2026-10-30.txt)も参考にする。

### 保存と組み込み

1. 横長3:2で作成し、原画像を `public/assets/cases/<case-id>/cover.png` に保存する。生成ツールの保存先だけに置かない。
2. 表示用に960×640pxの `cover.webp` を同じフォルダーへ作る。画質85を出発点とし、絵の見え方と容量を確認する。画像フォルダー内での変換例：

   ```sh
   cwebp -q 85 -resize 960 640 cover.png -o cover.webp
   ```

3. 一覧では `src/data/assets.ts` の `caseCover(caseId)` を使う。既定の参照先は `cover.webp`。PNGは原画像、既存のSVGは旧素材として扱う。追加形式を明示して参照する箇所がある場合は、その形式のファイルも確認する。
4. 画像の上に別の小物や書類を重ねない。構図全体が見えるよう、3:2の表示枠と `object-fit: contain` を保つ。
5. PNGとWebPを `assets.manifest.json` に登録し、件数、容量、形式、寸法、SHA-256、生成元を実ファイルに合わせる。`art_review` は `REQUIRED` とする。`qa/art-review.json` にも両方を登録し、人が承認するまでは `pending` とする。差し替え時も以前の承認を引き継がない。

### 確認

- PC幅とスマホ幅のケース一覧で、画像の読み込み、主役の見やすさ、欠け、横方向のはみ出しを確認する。他のケースと並べ、色と質感が世界観に合うかを見る。
- `npm run build`、`npm run test -- src/data/assets.test.ts src/data/assetManifest.test.ts src/screens/CaseSelectScreen.test.tsx`、`python3 scripts/validate_assets.py` を実行する。`qa/coverage.json` も確認し、素材の存在確認と人による公開承認を区別する。
- 機械検証やAIの目視確認だけで公開承認済みにしない。人による美術・権利の承認が終わるまでは未承認として記録する。

## データ契約

`v2` は `revision`（事件改訂）、`modes`、`decoding`、`graph`、`reportPrompt` を持つ。experiment / decision を方式として指定したら対応する設定が必須。解読optionの `evidence` はその選択を裏付けるすべての必要資料。図の経路はリンクの集合で、順番だけを正解にしない。詳細な型は `src/domain/v2Types.ts`、構造・参照検証は `data/schema/case.schema.json` と `src/data/validateCase.ts`。

実験設定は `conditions`、`choices`、`revealDocuments`、`comparisonPrompt`、`explanation`。意思決定設定は `objectives`、`options`（`cost`、`outcome`、`tradeoff`）、`resources`、`revealDocuments`、`updatePrompt`。資料ID・選択肢IDは実在し重複不可。根拠・開示資料を全て開ける予算を用意する。

## レビュー

- [ ] すべて架空であり、人格・能力・バイアス体質を診断しない。
- [ ] 事実誤認と、価値判断・保留・実験反応の違いが明確。
- [ ] 根拠はゲーム内にあり、未確認を虚偽と断定しない。
- [ ] 計算入力なしで成立し、複数資料の解読・比較・判断が必要。
- [ ] 別方針・判断維持・更新・資源不足に終了または回復の経路がある。
- [ ] 既存の事実・分母・正解キーをテストに合わせて改変していない。
- [ ] UIコードに事件IDや答えを埋め込まない。
- [ ] 素材はC-2正本を保ち、未審査を承認済みにしない。
- [ ] 事件専用の一覧画像を作成した。画像内に文字・ケース番号がなく、PNG原画像・表示用WebP・マニフェスト・審査記録がそろい、PC幅とスマホ幅で確認した。
- [ ] プレイヤーに見える文章は「文章の書き方」の手順を通し、`npm run lint:wording` が新しい指摘を出さない（`qa/wording-baseline.json` に足していない）。
- [ ] `npm run validate:cases` とアセット検証を行い、攻略・レビューを更新する。

## 文章の書き方

読み手は中学生とする。問いの文、選択肢、解説、結果の説明、`reportPrompt`、`data/ui/ja.json`、画面の文言が対象。作中の資料本文（`documents[].content`）は、現実の資料らしさを保つため語のチェックを警告にとどめるが、同じ読み手を想定して書く。

### 手順

1. **書く**: 1 文に用件は 1 つ。1 文はおよそ 60 字まで。何をすると何が起きるか（「資料をすべて貼ると根拠ありになる」）を、理由とともに書く。画面にあるボタン名と同じ言い方を使う（「採用する」ではなく「証拠ボードに貼る」）。
2. **機械で確かめる**: `npm run lint:wording` を実行する。`.yomiyasu-words/flag.txt` の語が出るか、1 文が長すぎると失敗する。`qa/wording-baseline.json` は仕組みを入れる前の文言を一時的に見逃す控えで、新しい指摘を足してはいけない。古い文言を直したら `node scripts/lint_wording.mjs --update-baseline` で控えを減らす。
3. **yomiyasu で推敲する**: 書いた文章を yomiyasu スキルに渡し、読み手を「専門知識のない人（general）」に指定する。スキルは `.yomiyasu-words/flag.txt`（避ける語）と `allow.txt`（残す項目名）を自動で読む。意味・条件・数値を変えずに言い回しだけを整え、「書き手に確かめたい点」に出た語は、説明を足すか言い換える。
4. **人が読む**: 中学生に説明するつもりで声に出して読み、分からない語が残っていないかを見る。

### 避ける語と言い換えの例

`.yomiyasu-words/flag.txt` の語は、次のように言い換える。新しい難しい語を見つけたら、`flag.txt` に 1 行足し、この表にも例を足す。

| 避ける語 | 言い換えの例 |
|---|---|
| 反実仮想 | ほかの方針を選んでいたらどうなっていたか（実際には起きていない想定） |
| 採用する／採用済み | 証拠ボードに貼る／ボードに貼った |
| 参照資料 | 答えのもとになる資料 |
| 暫定判断 | とりあえずの判断 |
| 一般化しない | 決めつけない |
| 妥当性 | 判断がよかったかどうか |
| 逆算しない | 結果から決めることはしない |
| 幸不幸 | 結果がよかったか悪かったか |
| 閲覧する | 開く、読む |
| 正誤 | 合っている・まちがっている |
| 骨子 | 骨組み |
| 追記 | 書き足す |
| 留保 | まだ決めきれないこと |
| 不確実性 | 分からないことが残ること |
| 整合する | 食い違わない |
| 有限 | 限りがある |
| 前段 | 前の段階 |
| 矯正 | 直す |
| 唯一解 | ただ一つの正解 |

項目名として定着している語（補強・反証・適用範囲・時系列、根拠、仮説、前提、方針、保留、調査予算）は `.yomiyasu-words/allow.txt` にあり、言い換えない。代わりに、その語の意味を画面の説明文で書く（証拠ボードの「役割の意味」のように）。

## V2の役割付き根拠経路

`v2.graph.paths` は必要な関係の集合を経路ごとに定義します。経路のいずれか一つが成立すれば根拠関係を満たします。`from` / `to` は異なる資料IDで、`relation` は `supports`（補強）、`contradicts`（反証）、`qualifies`（適用範囲・条件）、`sequence`（時系列）です。方向も条件に含みます。複数の妥当な経路を持つ事件で最初の経路だけを唯一解として扱わないでください。

`graph.prompt` は比較の目的を伝え、必要資料名・正答の関係ラベルの組み合わせを明かしません。解読選択肢の根拠には、各 `options[].evidence` の全資料が必要です。異なる資料から成立する別解は、別の `accepted: true` の選択肢として定義できます。任意の線を増やすだけでは完了せず、資料を読み・採用し、役割を含む経路を作る必要があります。
