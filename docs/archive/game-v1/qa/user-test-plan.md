# 利用者テスト計画（MVP-044）

- ステータス: **計画のみ。利用者テストは未実施（0 / 5 人）。**
- 目的: `docs/TEST_STRATEGY.md`「UX検証（未実施）」の観察項目を、再現可能な手順と記録フォーマットに落とす。
- 対象ビルド: `integration/wave-2a` 以降の静的ビルド（`npm run build` → `dist/`）。テスト時のコミット SHA を各セッション記録に残す。
- 関連: `docs/qa/user-test-session-template.md`（観察者シート）、`docs/qa/user-test-consent.md`（同意文）、`qa/user-tests/README.md`（記録フォーマット）、`scripts/summarize_user_tests.mjs`（集計）、`.github/ISSUE_TEMPLATE/user-test-finding.md`（改善 Issue）。

## 1. 何を確かめたいか

`docs/MVP_SPEC.md` 3 章（ターゲット）・4 章（プレイ時間と難易度）・13 章（受け入れ基準）と `docs/TEST_STRATEGY.md` の UX 検証項目から、観察項目を次の 6 つに固定する。各項目は `qa/user-tests/session-template.json` の対応フィールドに記録する。

| # | 観察項目 | 根拠 | 判定の目安 | 記録先フィールド |
| --- | --- | --- | --- | --- |
| O1 | **口頭補足なしで進められるか**: 事件の導入・ルール説明を観察者が口で補わずに CASE 01 を進められる | SPEC 3 章「認知バイアスの知識は不要。プレイに必要な情報は資料として提供」 | 観察者の「助け舟」（3 章参照）が 0 回なら達成。1 回以上なら、何を補ったかを記録 | `ran_without_verbal_help`, `cases[].help_given[]` |
| O2 | **分かりづらいルール vs 難しいが納得できる推理の区別**: 参加者が詰まったとき、原因がルール・UI の不明瞭さか、推理そのものの難しさか | TEST_STRATEGY「分かりづらいルールと、難しいけれど納得できる推理を区別」、GAME_RULES 8 章 | 詰まり箇所ごとに `kind` を `rule_unclear` / `ui_unclear` / `reasoning_hard` / `content_unclear` のいずれかに分類。事後インタビューの Q3・Q4 で参加者自身の言葉と突き合わせる | `stuck_points[].kind` |
| O3 | **ミス後に次の手が思いつくか**: 不掲載・不正解のあと、何を変えるか自分で言えるか | TEST_STRATEGY「ミスした時に次に何を変えるか思いつくか」、SPEC 5.6「失敗時は不足した種類を示し」 | 失敗直後に観察者が「次はどうしますか」とだけ聞き、具体的な次の操作（別の資料を開く、照合を変える 等）を言えれば `yes` | `after_mistake` |
| O4 | **紙の装飾が可読性を阻害していないか**: 切り抜き・スタンプ・紙テクスチャが数値や本文の読み取りを妨げていないか | TEST_STRATEGY「机上の紙の切り抜きが情報の可読性を阻害していないか」、SPEC 14 章「モバイルの証拠ボード」 | 読み間違い・読み飛ばし・拡大操作・「読みにくい」発言があれば記録。端末種別とビューポート幅を必ず残す | `readability`, `device` |
| O5 | **楽しさ**: 5 段階の自己申告と、どの瞬間が楽しかった／退屈だったか | SPEC 1 章「体験目標」 | 数値だけでなく瞬間（画面・操作）を記録する | `fun`, `fun_comment` |
| O6 | **理解**: 事件の論点（例: CASE 01 なら「母数が違う 2 つの比率」）を自分の言葉で説明できたか | SPEC 5.7、GAME_RULES 8 章「当てっこを避ける」 | 事後インタビュー Q1 で、解説画面の文言をなぞるのではなく自分の言葉で言えたら `yes`、部分的なら `partial` | `understanding` |

受け入れ条件（Issue #44）の「詰まり箇所 / 楽しさ / 理解 / 完走率」は、それぞれ `stuck_points[]` / `fun` / `understanding` / `cases[].completed` から集計する。

### 記録しないこと（倫理上の制約）

`AGENTS.md` と `docs/CONTENT_POLICY.md` に従い、**参加者の人格・能力・認知特性の評価を一切記録しない**。

- 書いてよいのは「画面・操作・時刻・参加者の発言の引用・観察者が見た事実」。
- 「理解が遅い」「注意力がない」「○○バイアスにかかっていた」「向いていない」のような参加者への評価は書かない。ゲーム内の解説も、参加者の特性に結びつけない。
- 氏名・所属・連絡先・年齢（10 歳刻みの年代も含む）・性別は取らない。参加者番号（`P01`〜）のみ。
- 画面の録画・音声録音は行わない。観察者の手書き／タイピングのメモのみ。
- `scripts/summarize_user_tests.mjs` は自由記述に評価語（性格・能力 等）が混入していないかを機械的に確認し、見つかればエラーにする。これは補助であり、観察者の自制を置き換えない。

## 2. 参加者

- 目標人数: **5 人以上**（Issue #44）。初見プレイが条件。本リポジトリの開発者・レビュアーは除く。
- 募集条件は SPEC 3 章に合わせる: 16 歳以上で、パズル／ニュース／マーケティングのいずれかに関心がある人。認知バイアスの事前知識は不要（むしろ無い人を含める）。
- 端末の混在を意図的に作る: 5 人中、スマートフォン 2 人以上・PC 2 人以上を目安にする（SPEC 13 章「PC/スマートフォンで致命的なレイアウト崩れがない」）。
- 参加者には `docs/qa/user-test-consent.md` を読んでもらい、口頭で同意を得る。署名や氏名記入は求めない。

## 3. セッション手順（60 分）

1 セッション = 参加者 1 人 + 観察者 1 人（可能なら記録係をもう 1 人）。時間は目安で、CASE 01 を優先する。

| 時間 | 内容 | 観察者の動き |
| --- | --- | --- |
| 0:00〜0:05 | **導入（5 分）** | 同意文を見せて口頭で同意を得る。次の 3 点を**必ず**伝える: (a) これは心理診断ではなく、遊び方の分かりやすさを調べるテストである。評価されるのはゲームであって参加者ではない。(b) 登場する企業・人物・数字はすべて架空である。(c) 途中でやめてよい。ルールや事件の内容はここでは説明しない（O1 のため）。 |
| 0:05〜0:15 | **チュートリアル** `#/tutorial` | 操作の観察のみ。チュートリアルで詰まった箇所も `stuck_points` に `case_id: "tutorial"` で記録する。 |
| 0:15〜0:40 | **CASE 01**「消えた55人の利用者」 `#/play/case-01` | 主観察区間。発話思考（考えていることを声に出してもらう）を依頼するが強制しない。失敗したら Q「次はどうしますか」のみ聞く（O3）。助け舟は 4 章の条件でのみ。 |
| 0:40〜0:50 | **CASE 02**「半額セールの値札」（時間があれば） | CASE 01 が 0:40 までに終わらなければ CASE 02 は行わず、インタビューに進む。CASE 02 は「2 件目で型が読めるか」（GAME_RULES 9 章）の参考観察。 |
| 0:50〜1:00 | **事後インタビュー（10 分）** | 5 章の質問リストを順に。誘導せず、答えは参加者の言葉のまま引用で記録。 |

セッション後 15 分以内に、観察者は `qa/user-tests/session-template.json` をコピーして `qa/user-tests/P01.json` のように保存する（記憶が新しいうちに）。

## 4. 観察者の記録ルール

- **誘導しない。** 「ここをタップしてみたら？」「この資料が怪しくない？」は禁止。質問されたら「どうすると思いますか？」と返し、その質問を `stuck_points` に記録する。
- **助け舟を出す条件**（これ以外では助けない。出したら `cases[].help_given[]` に時刻・理由・内容を記録し、O1 は未達成とする）:
  1. 同じ画面で **3 分以上**操作が止まり、参加者が「分からない」と明言した。
  2. 調査予算が尽きて必要資料が開けない状態（詰み。`docs/reviews/budget-dead-end-analysis.md` 参照）で、リセット操作に **2 分以上**気付かない。
  3. アプリの不具合（表示崩れ・保存失敗など）で進行不能になった。この場合は不具合として `stuck_points[].kind: "bug"` を記録し、再読み込み等で復帰させる。
  4. 参加者が中断を希望した（助け舟ではなく終了。`completed: false` と `ended_reason` を記録）。
- 助け舟の内容は**最小限**にする。「画面のどこかに今の状態を変える操作があります」のように場所を指さない表現から始め、それでも進まない場合のみ操作名を言う。答え（必要資料・照合ペア・数値・断片）は絶対に言わない。
- 詰まり箇所は**画面・操作・時刻**の 3 点を必ず記録する（例: `00:12 / board / link_select`）。画面名の一覧は `qa/user-tests/README.md`。
- 参加者の発言は要約せず引用する。評価語を使わない（1 章「記録しないこと」）。
- 観察者の推測（「おそらく〜と誤解している」）は `observer_notes` に、事実と分けて書く。

## 5. 事後インタビュー質問リスト（10 分）

順番どおりに聞き、答えは引用で記録する。「はい／いいえ」で終わったら「もう少し詳しく」とだけ促す。

1. **（理解 O6）** さっきの事件（CASE 01）で、記事が正しかった／間違っていたのはなぜでしたか。自分の言葉で説明してください。
2. **（楽しさ O5）** いちばん面白かった瞬間と、いちばん退屈だった瞬間はどこでしたか。楽しさを 5 段階（1 = 退屈、5 = とても楽しい）で言うと？
3. **（区別 O2）** 詰まったところがあれば、それは「ルールや画面が分かりにくかった」からですか、「問題自体が難しかった」からですか。
4. **（区別 O2 / 納得）** 答え合わせを見て、納得できましたか。「それは無理だ」と感じた点はありますか。
5. **（次の手 O3）** 不掲載になったとき、次に何を変えればいいか見当がつきましたか。
6. **（可読性 O4）** 紙や切り抜きの見た目で、数字や文章が読みにくいと感じた場所はありましたか。
7. **（口頭補足 O1）** 始める前に説明してほしかったことはありますか。
8. **（自由）** 他に気になったことがあれば何でも。
9. **（終了時の確認）** 「今日の内容は、あなたの考え方や性格を判定するものではありません」と改めて伝える。参加者の質問に答える。

## 6. 集計と改善

1. 全セッションの JSON を `qa/user-tests/` に置き、`npm run summarize:user-tests` を実行する。完走率・平均所要時間・楽しさの分布・理解度の分布・詰まり箇所の頻度（画面別・画面×操作別）・重大度別件数が Markdown 表で出力される。
2. 詰まり箇所を**重大度**で並べ、上位から `.github/ISSUE_TEMPLATE/user-test-finding.md` を使って Issue を起票する。重大度の定義:

| 重大度 | 定義 | 対応 |
| --- | --- | --- |
| `blocks_completion`（完走を妨げる） | その箇所で先に進めない、または助け舟なしでは進めなかった | 次のリリース前に必ず修正 |
| `misleads`（誤解を生む） | 進めはするが、ルール・事件の内容を誤って理解させる（例: 母数の違いが伝わらない、照合の意味を取り違える） | 原則修正。文言・導線の変更で対応 |
| `unpleasant`（不快） | 進行と理解は妨げないが、いらだち・疲れ・読みにくさを生む | 複数人で再現すれば修正 |
| `preference`（好み） | 個人の好みの範囲（色・音・言い回し） | 記録のみ。3 人以上で一致すれば検討 |

3. 同じ箇所が 2 人以上で再現した詰まりは、1 人だけのものより優先する。集計の「詰まり箇所の頻度」表の `参加者数` 列がその根拠になる。
4. 「推理が難しい」（`reasoning_hard`）は欠陥ではない（SPEC 4 章「高難易度を優先」）。ただし Q4 で「納得できない」が付いた場合は `misleads` として扱い、`docs/walkthrough/` と突き合わせて事件データ側を見直す。**テストを通すために正解キーを変えない**（`AGENTS.md`）。
5. 改善を入れたら、同じ手順で再テストする。前回の参加者は初見でなくなるので新しい参加者を募る。

## 7. 成功の目安（MVP としての合格ライン）

Issue #44 は記録が条件であり合格ラインは別途決めるが、改善の優先順位付けのために次を暫定の目安とする。

- CASE 01 完走率（助け舟なし）: 5 人中 3 人以上。
- CASE 01 所要時間: 中央値が SPEC 4 章の「標準ケース 5〜10 分」の 2 倍（20 分）以内。
- `blocks_completion` の詰まりが 2 人以上で再現: 0 件。
- 理解度 `yes` + `partial`: 5 人中 4 人以上。
- 楽しさの平均: 3.0 以上。

これらは実測後に見直す。未達でも、人格・能力に原因を求めない。
