# 事件データ制作ガイド

## 1. 基本手順

1. 題材を選ぶ（買い物、マーケティング、仕事、ニュースなど）。
2. 見出しの主張を決め、**事実だけで答えを確定できる数値・期間・対象集団**を設計する。
3. 必須の資料3件と、正しい関連付け1組を設計する。
4. 必要ではないが調べる合理性がある資料2〜3件を加える。
5. 資料を読み計算しないと解けない検証メモ2題を作る。
6. 断片8枚（正しい3、もっともらしい誤り5）を作る。
7. 「誇張」「フレーミング」「データの解釈」のどの問題か区別して解説を書く。
8. 人手で複数の解釈が成立しないか検証する。

## 2. JSONフォーマット

```json
{
  "id": "case-XX",
  "title": "事件タイトル",
  "bias": "主題",
  "difficulty": "HARD",
  "estimated_time": "5〜10分",
  "intro": "依頼文",
  "budget": 4,
  "documents": [{"id":"ad","title":"広告","content":"資料本文","cost":0,"visual":"advert"}],
  "required_evidence": ["a","b","c"],
  "required_link": ["a","c"],
  "link_prompt": "主張の数字と、その元になった数字を突き合わせる 2 枚を結びます。",
  "analysis_tasks": [{"id":"calculation","prompt":"割合を求める","unit":"%","expected":45,"tolerance":0.1}],
  "headline_fragments": [
    {"id":"f0","text":"断片の文章","kind":"correct","reason":"正しい理由を1文で","evidence":["a"]},
    {"id":"f3","text":"誤った断片","kind":"overgeneralization","reason":"誤りの理由を1文で","evidence":["a","c"]}
  ],
  "correct_fragments": ["f0","f1","f2"],
  "debrief": {"explanation":"今回の種明かし", "takeaway":"今後の見方"},
  "disclaimer": "架空のケースです"
}
```

（上のJSONは構造説明の抜粋です。実際のMVPは検証メモ2件と見出し断片8件が必要です。）

### 照合の問い `link_prompt`（必須）

証拠ボードと記事画面に表示する、「この事件では何を突き合わせるのか」の一文（10〜120 文字）。プレイヤーが組み合わせを総当たりで探さなくて済むようにする一方で、正解を名指ししないこと。

- 資料のタイトルをそのまま含めると検証で拒否される（`validateCase` / `npm run validate:cases`）。
- 「主張」と「その根拠や元データ」のように、資料の**役割**で書く。例: 「見せ方（グラフ）と、その元になった数字。この 2 つを突き合わせる 2 枚を結びます。」
- `required_link` の 2 枚が、この問いに対して他の組み合わせより明らかに妥当であることを確認する（別解があるなら JSON モデル側を見直す）。

### 断片の `kind` / `reason` / `evidence`（任意、推奨）

各 `headline_fragments[]` には、誤誘導の理由を説明するための任意フィールドを付けられる。結果画面での理由表示に使う。

| フィールド | 型 | 内容 |
| --- | --- | --- |
| `kind` | 列挙 | 断片の種別。`correct`（正解）、`overgeneralization`（理由なく全体に一般化）、`misread-statistic`（統計の誤読: 分母・指標の取り違え、相対変化の誇張など）、`causal-claim`（原因・結論の断定）、`ignored-counter-evidence`（反対資料の無視）、`unverifiable`（資料からは検証できない主張）、`other` |
| `reason` | 文字列（5〜120 文字） | その断片が誤り（または正しい）である理由を **1 文** で。資料の数値や記述に基づいて書き、プレイヤーの人格や能力には触れない |
| `evidence` | 資料 ID の配列（1〜6 件、重複なし） | `reason` の根拠となる資料。`documents[].id` に実在すること |

規則（`npm run validate:cases` と読込時の `validateCase` が検査する）:

- 3 つのフィールドはそれぞれ任意だが、付けるなら型・列挙・参照整合を満たすこと。
- `correct_fragments` に含まれる断片の `kind` は必ず `correct`、含まれない断片の `kind` は `correct` 以外（両方向）。採点は `correct_fragments` だけで決まり、`kind` は表示用の付加情報。**`kind` を付け替えて答えを変えない。**
- 誤りの `reason` は「どの資料のどの記述で否定できるか」を書く。意地悪ではなく「ありそうな誤読」の説明にする。

詳しくは `data/schema/case.schema.json`。現行試作は `required_evidence` を3件に固定した配点なので、4件以上に拡張する時は採点を再設計する。

## 3. 執筆時のチェックリスト

- [ ] 計算式と本文に齟齬がない。
- [ ] 広告・ニュースの主張と、一次データの主張を分けている。
- [ ] 確認できない因果関係を断定していない。
- [ ] 「間違った意思決定」を必ず一つに決めつけていない。
- [ ] 推理のための情報がゲーム内部に存在する。
- [ ] 必須資料を全部開ける予算がある。
- [ ] `link_prompt` が資料名を使わずに照合の目的を伝えている。
- [ ] 誤誘導は意地悪ではなく「ありそうな誤読」になっている。
- [ ] 専門語を知らなくても論理で解ける。
- [ ] ユーザーの人格や能力を断定しない。
- [ ] 実在の企業・人物・記事と誤認されない。

## 4. 事件の公平性

たとえば「90%が継続」は、分母が明示されていなければ誤解を生む場合があるが、直ちに虚偽と断定できるとは限らない。プレイヤーは**どの範囲に対して正しい数値か**を示す記事を作る。正解の核は真偽の二択ではなく、適用範囲の明確化。

## 5. テストデータの生成

このパッケージでは `scripts/make_cases.py` で5事件のJSONを生成している。事件を編集する際、**生成スクリプトとJSONを一致させる**運用にするか、編集対象をJSONへ一本化してスクリプトを廃止するか決める。初期はJSONを原本とし、スクリプトは再生成用に残すのが簡単。
