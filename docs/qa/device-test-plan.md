## 2. 準備

### 2.1 配信

| 方法 | 用途 | 手順 |
| --- | --- | --- |
| LAN 配信（HTTP） | ブラウザモードの全項目 | PC と端末を同じ Wi-Fi に接続し `scripts/serve_lan.sh --build` を実行。表示された `http://<PCのIP>:4173/` を端末で開く |
| GitHub Pages（HTTPS） | PWA モード（Android の「インストール」は HTTPS 必須）、本番相当のサブパス `/URAMEKU/` | MVP-045 のデプロイ後に公開 URL を開く。未デプロイの間は HTTPS トンネル（任意のもの）を LAN 配信の前段に置いてもよい |

- `VITE_BASE_PATH=/URAMEKU/ scripts/serve_lan.sh --build` でサブパス配信を LAN でも再現できる。
- 検証するビルドのコミット SHA（`git rev-parse --short HEAD`）を記録表の「ビルド」に書く。

### 2.2 端末側の初期状態

1. 対象ブラウザのサイトデータ（当該 URL の localStorage）を削除し、初回訪問と同じ状態にする。iOS: 設定 > Safari > 詳細 > Web サイトデータ。Android: Chrome のサイト設定 > ストレージ。
2. 文字サイズ・ページズームを 100% に戻す（M11 で 200% にする）。
3. 音量を中程度にし、iOS はサイレントスイッチ OFF（鳴る側）にしておく（M02 で切り替える）。
4. 機内モード OFF。
5. 効果音の検証（M01〜M03）は、効果音を画面に組み込む PR が統合されたビルドで行う。`integration/wave-2a` 時点では `useSound` の呼び出しは `AudioControl`（設定画面）にしかなく、設定画面はまだプレースホルダーのため、組み込み前のビルドでは「音が鳴らない」のは不具合ではない。記録表の前提欄にビルドの状態を書く。

### 2.3 記録

- 記録表は端末 1 台（1 モード）につき 1 セクション。`docs/qa/device-test-log.md` のテンプレートを複製する。
- 結果は `pass` / `fail` / `blocked`（前提未達で実施不能）/ `not-run` の 4 値。
- `fail` は再現手順・スクリーンショット（または画面録画）を添え、GitHub Issue を起票して番号を書く。
- 重大度は次の定義に従う。

| 重大度 | 定義 | 受け入れへの影響 |
| --- | --- | --- |
| S1 重大 | 進行不能、保存の消失、音が一切出ない、復帰後に状態が壊れる | 1 件でも不合格 |
| S2 高 | 主要機能の不良だが回避策がある（例: リロードで直る） | 修正または回避策の明記が必要 |
| S3 中 | 見た目・操作感の問題。進行と保存には影響しない | Issue 化して次の波へ |
| S4 低 | 仕様どおりだが改善余地がある、または情報 | 記録のみ |

## 5. 判定

- 端末 1 台（1 モード）の総合判定: S1 が 0 件かつ P0 シナリオに `fail` が無ければ `pass`。S1 が 1 件でもあれば `fail`。前提未達（効果音未組み込み、HTTPS 未配信）で過半が実施できなければ `blocked`。
- Issue #42 の受け入れ条件は、P0 の 5 対象がすべて `pass` で満たす。
- `qa/device-matrix.json` の各 `result` / `tested_at` / `tester` / `build` を更新し、PR で提出する。
